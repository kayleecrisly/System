# 实验设计：基于真实固件评估外设模型的 Rehosting 效果

## 实验目标与阶段

当前阶段通过官方示例和已有驱动构建外设功能测试固件，在集成系统生成模型的 QEMU 中运行，评估固件启动、驱动初始化和目标外设操作的执行情况。OpenTitan 和 Wujian100 是验证案例，系统生成规则保持通用。

首批项目版本、固件候选、运行依赖及环境缺口见[硬件基线与固件候选清单](BASELINE.md)。

较高保真度是模型的设计预期。RTL／真实硬件行为对照、边界条件和时间行为等系统性的保真度（faithfulness）验证在后续补充，不作为当前 rehosting 实验的前置条件。当前测试通过的结论限定于已执行的固件和功能。

## 系统职责与实验边界

系统主要根据 RTL/MLIR 和经过确认的硬件描述生成外设模型、QEMU 包装及板级文件。CPU 复用兼容的现有 QEMU 实现；实验负责准备固件、软件环境、运行输入和结果检查。

- 被测外设必须实际使用系统生成的模型；CPU、内存、中断控制器等配套组件的来源和支持范围单独记录。
- 板级文件描述目标硬件的地址映射、组件连接和启动配置，实验控制与结果判断放在固件或主机脚本中。
- 输入通过串口、引脚等对应接口提供；按需准备 SPI／I²C 对端等环境。不通过强改模型内部状态、伪造完成条件或跳过驱动等待来让测试通过。
- 未实现的启动流程、时钟复位或组件连接按用例依赖处理。若采用简化加载或启动方式，明确记录，不能据此声称已验证完整芯片启动。

生成器软件回归测试位于 `../tools/tests/`，通过 CTest 运行；本目录的实验使用目标 CPU 执行固件，验证生成平台的 rehosting 能力。

## 固件来源与适配原则

参考 [P2IM 论文 §5.1](https://www.usenix.org/system/files/sec20-feng.pdf#page=11)及其[单元测试仓库](https://github.com/RiS3-Lab/p2im-unit_tests)，按外设功能、软件环境和目标平台组织用例。P2IM 既复用现成示例，也使用适配或修改后的测试程序：例如 Arduino ADC 复用官方读取模拟电压示例，RIOT TIMER 基于应用模板加入定时器操作。

优先复用与目标 RTL 版本和硬件配置匹配的官方示例、驱动测试。已有示例覆盖目标功能时直接使用；覆盖不足时做最小适配与功能补充，保留真实驱动执行路径。记录来源、版本和修改内容，区分原始示例、适配示例、新增功能用例。配置引脚、通道或增加结果检查属于可记录的适配，不能为了适应错误模型而改变被测硬件操作。

## 硬件版本与软件环境

先确定被转换的 RTL 版本、模块参数和 SoC 配置，再选择兼容的寄存器定义、驱动、SDK、固件及编译工具。优先使用同一项目版本中的配套资料；跨版本使用时核对地址、寄存器、中断和启动要求。已有 MLIR 需确认其实际 RTL 来源，不能默认与最新官网示例匹配。

OS 按用例需要选择，不预设必须使用 Zephyr 或其他 RTOS。裸机示例使用对应 SDK 和工具链；带 OS 的示例还需匹配的 OS 版本、目标板支持和构建配置。

| 项目 | 可考察的软件与 CPU 基础 | 选取时需确认 |
|---|---|---|
| OpenTitan | 官方驱动与设备测试框架 OTTF；QEMU 的 Ibex／lowRISC OpenTitan CPU 实现 | 与 RTL 对应的软件版本、启动方式、测试平台依赖和 CPU 特性 |
| Wujian100 | 官方 SDK 驱动示例，按需使用 RTOS 示例；玄铁 QEMU 的 E902 系列实现 | 指令集、ABI、中断机制和专用控制寄存器配置 |

[OTTF](https://opentitan.org/book/sw/device/lib/testing/test_framework/) 是设备端测试框架源码，与具体测试、驱动和启动代码一起编译成测试固件，由目标 CPU 执行。它提供测试入口、检查、日志和结果报告；使用 OTTF 不代表该测试天然支持 QEMU，仍需确认依赖。只有选取 Zephyr 用例时才配置相应 Zephyr 环境。

CPU 实现存在不等于已经验证固件兼容性。例如玄铁 QEMU 中 `e902` 与 `e902m` 的主要区别是后者启用整数乘除法 M 扩展；最终配置应由目标硬件和固件要求确定。

## 实施流程

1. **确定硬件基线。** 核对 RTL、MLIR、手册、bindings 和板级描述的版本与配置；需要重转时使用系统配置的新版 CIRCT，并记录版本和输入。
2. **整理固件候选。** 列出示例来源、被测功能、软件环境、硬件依赖和通过条件。首批优先选择依赖较少的 UART、GPIO、定时器等用例，具体顺序由依赖决定。
3. **建立编译环境。** 优先编译原始示例，按需适配并记录，产出 ELF 等目标固件及可重复构建的命令。
4. **配齐运行依赖。** 明确 CPU、内存、启动入口、时钟复位、中断和外部输入需求，标明生成、复用及尚待支持的组件。
5. **生成并集成平台。** 生成外设模型和板级文件，集成至选定版本的 QEMU，确认被测地址连接到生成模型。
6. **运行并分析。** 提供输入、收集证据，分别定位版本、环境、连接和模型问题。先完成一个可重复用例，再扩展功能、外设和软件环境组合。

## 通过条件与结果记录

每项测试在运行前确定输入、预期操作、观察方式和完成条件。通过至少需要固件正常启动、完成必要初始化、实际执行目标操作并满足该用例的检查条件；不能仅以有日志、未崩溃或未超时判定。常驻循环固件通过观察指定事件或操作进展判断，不能把正常循环直接视为停滞。

尚未编译、缺少运行依赖和已执行失败分别记录；报告通过率时明确用例集合与未执行原因，避免混淆环境就绪程度和 rehosting 效果。当前不以周期精确对照作为统一通过条件。

| 记录项 | 内容 |
|---|---|
| 来源与版本 | RTL/MLIR 来源、固件示例版本、用例类别及修改内容 |
| 环境与组件 | SDK／OS／编译器／CIRCT／QEMU 版本，CPU 配置，生成与复用组件 |
| 测试定义 | 目标功能、输入、预期结果、完成条件及参考依据 |
| 复现与结果 | 构建和运行命令、对应产物、执行日志、结果及失败原因 |

## 文件组织

以下路径均相对于 `System/`，生成和运行使用独立批次目录。

| 路径 | 保存内容 |
|---|---|
| `experiments/<项目>/firmware/src/` | 固件源码、启动代码、链接脚本及构建配置 |
| `experiments/<项目>/firmware/build/<批次>/` | 编译产物，如 ELF、BIN |
| `experiments/<项目>/host-test/` | 主机端运行、输入提供、结果检查脚本 |
| `outputs/<项目>/<批次>/` | 生成的外设模型、板级文件及必要配置和清单 |
| `results/<项目>/<批次>/generation/` | 生成日志、中间 MLIR 等过程记录 |
| `results/<项目>/<批次>/execution/` | 固件执行日志、实验记录及验证结果 |

本文件记录实验设计与推进方式，具体用例及执行结果在实施时补充。
